01

The Big Picture

🟠 In Plain English

Speech-to-text takes real time to run — long enough that making a user's app just sit there and wait would feel broken. So the ASR service never makes anyone wait: the backend sends the audio, the ASR service instantly says "got it, working on it," and processes it in the background. The moment it's done, the result shows up in a queue the backend is watching — and the backend takes it from there (updating a record, sending a push notification, whatever the product needs).

.NET BackendPOST /transcribe (multipart file)
↓
ASR Servicereplies 202 Accepted immediately
↓
RabbitMQASR service processes in the background
↓
.NET Backendconsumes result from asr.transcription.results
🔧 Technical Detail

Two separate legs, two separate protocols:

  • Request leg — HTTP. Backend calls POST /transcribe on the ASR service directly. Response is 202 Accepted in well under a second, containing a request_id.
  • Result leg — RabbitMQ. The backend consumes the asr.transcription.results queue. Messages there are keyed by the same request_id, published whenever a job finishes (success or failure).

The backend never polls the ASR service for status. It reacts to messages arriving on the results queue.

There is also an asr.transcription.requests queue — that's internal to the ASR service (API layer → background worker) and the backend should never publish to or consume from it directly. The only supported way to submit a job is the HTTP endpoint in §3.

03

Step 1 — Send the Audio (HTTP)

🟠 In Plain English

A normal file upload, like any REST API. The only thing to remember: the response you get back is not the transcript — it's just a receipt confirming the job was accepted. The real transcript arrives later, over RabbitMQ (§4).

🔧 Technical Detail

POST/transcribe

Content-Type: multipart/form-data

FieldTypeRequiredNotes
filebinary (form file)YesSupported extensions: .wav, .mp3, .flac, .m4a. Max size: 25 MB (configurable server-side).
languagestring (form field)NoDefaults to "Arabic" if omitted.

Optional header: X-Request-ID — if the backend already has a correlation ID (e.g. from the original client request), pass it here and the ASR service will use it instead of generating its own. If omitted, the service generates a UUID and returns it in the response body.

Response: 202 Accepted

⚠ Common mistake

Do not treat this response as the transcript, and do not poll /transcribe again for status — there is no status-polling endpoint. Store the request_id and wait for the matching message on the results queue.

04

Step 2 — Receive the Result (RabbitMQ)

🟠 In Plain English

The backend keeps a listener running against one queue. Whenever the ASR service finishes a job — successfully or not — a message shows up there. That message has everything needed: which request it belongs to, whether it worked, and the transcript (or the failure reason).

🔧 Technical Detail

Queue: asr.transcription.results — durable, so messages survive a RabbitMQ restart.

Message body: UTF-8 JSON, content_type: application/json, delivery_mode: persistent.

Delivery guarantee: the ASR service acknowledges its own internal job only after successfully publishing this message, so a crash mid-processing does not silently drop a result — worst case the job is retried and a duplicate message could theoretically appear. Consumers should be written to tolerate a duplicate request_id safely (see §9).

Full field reference in §5.

⚠ Note

Failure messages intentionally do not include a raw error string or stack trace — per the platform's error-handling standard, internal details are never exposed outside the service. If a specific failure needs investigating, check the ASR service's own logs (searchable by request_id).

06

C# — Sending a Request

🟠 In Plain English

Standard multipart upload using .NET's built-in HttpClient — nothing ASR-specific about the mechanics, just the field names to match.

using var httpClient = new HttpClient { BaseAddress = new Uri("http://<asr-service-host>:8000") };

using var form = new MultipartFormDataContent();
using var fileStream = File.OpenRead("clip.wav");
using var fileContent = new StreamContent(fileStream);
fileContent.Headers.ContentType = new MediaTypeHeaderValue("audio/wav");

form.Add(fileContent, "file", "clip.wav");
form.Add(new StringContent("Arabic"), "language");

using var request = new HttpRequestMessage(HttpMethod.Post, "/transcribe") { Content = form };
request.Headers.Add("X-Request-ID", correlationId.ToString()); // optional — omit to let the service generate one

var response = await httpClient.SendAsync(request);
response.EnsureSuccessStatusCode(); // expect 202

var body = await response.Content.ReadFromJsonAsync<TranscribeAcceptedResponse>();
var requestId = body.Data.RequestId; // store this — it's how you'll match the result later

Matching C# record for the response shape:

public record TranscribeAcceptedResponse(bool Success, string Message, object? Metadata, TranscribeAcceptedData Data);
public record TranscribeAcceptedData(string RequestId, string Status);

C# — Consuming Results

🟠 In Plain English

A long-running listener (a hosted background service, in ASP.NET Core terms) that stays connected to RabbitMQ and reacts every time a result message arrives — this is where the backend actually finds out a transcription finished and can trigger whatever comes next (saving to the database, pushing a notification, etc).

🔧 Technical Detail

Uses the official RabbitMQ.Client NuGet package. Example below is a minimal BackgroundService — adapt to your existing hosting/DI setup.

public class AsrResultsConsumer : BackgroundService
{
    private const string QueueName = "asr.transcription.results";

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var factory = new ConnectionFactory
        {
            HostName = "<rabbitmq-host>",
            Port = 5672,
            UserName = "<user>",
            Password = "<password>",
            VirtualHost = "/"
        };

        using var connection = await factory.CreateConnectionAsync(stoppingToken);
        using var channel = await connection.CreateChannelAsync(cancellationToken: stoppingToken);

        await channel.QueueDeclareAsync(QueueName, durable: true, exclusive: false, autoDelete: false, cancellationToken: stoppingToken);

        var consumer = new AsyncEventingBasicConsumer(channel);
        consumer.ReceivedAsync += async (model, ea) =>
        {
            var json = Encoding.UTF8.GetString(ea.Body.ToArray());
            var result = JsonSerializer.Deserialize<AsrResultMessage>(json);

            if (result.Success)
            {
                // e.g. save result.Data.Transcript against result.Metadata.RequestId,
                // then notify the relevant user
            }
            else
            {
                // e.g. mark the job failed, log result.Metadata.RequestId for follow-up
            }

            await channel.BasicAckAsync(ea.DeliveryTag, multiple: false);
        };

        await channel.BasicConsumeAsync(QueueName, autoAck: false, consumer, stoppingToken);

        await Task.Delay(Timeout.Infinite, stoppingToken);
    }
}

Matching C# records for the result message:

public record AsrResultMessage(bool Success, string Message, AsrMetadata Metadata, AsrTranscriptData? Data);
public record AsrMetadata(string RequestId, double ProcessingTime);
public record AsrTranscriptData(string Transcript, string Language);

Error Handling

ScenarioWhat happensBackend should
Unsupported audio formatPOST /transcribe returns 400 immediately (not queued)Surface the error at upload time — no result message will ever arrive for this attempt, since no request_id was issued
File too large (>25MB)400 immediately, same as aboveSame — handle synchronously at upload time
Transcription fails after being queued202 was already returned; a failure message (§5.2) later arrives on the results queueWatch for success: false in consumed messages, not just HTTP status codes
ASR service is downPOST /transcribe connection fails / times outStandard HTTP retry/backoff on the backend's side; no job was created, so nothing to correlate
RabbitMQ briefly unavailableASR service auto-reconnects (robust connection) and retains queued jobs — durable queue survives a broker restartBackend consumer should also reconnect automatically; no messages are lost, only delayed
09

Correlation & Idempotency

🟠 In Plain English

Always use request_id to match a result back to the original request — never assume ordering or timing. And because message queues can, in rare failure scenarios, deliver the same message more than once, the backend's handling of a result should be safe to run twice without causing problems (e.g. use an "upsert" rather than an "insert" when saving the transcript).

🔧 Technical Detail
  • request_id is a UUID, generated either by the backend (via X-Request-ID) or by the ASR service if omitted — always present and always the correlation key.
  • Jobs are processed one at a time per ASR worker (RABBITMQ_PREFETCH_COUNT=1 by default) — no guarantee of completion order matching submission order if multiple requests are in flight.
  • Design the result handler to be idempotent on request_id (e.g. UPDATE ... WHERE request_id = ... rather than assuming a fresh insert).

Environment Checklist

🟠 In Plain English

Before wiring this up in staging or production, confirm these values with whoever owns the ASR service deployment — the ones in this document are local dev defaults and will not work as-is anywhere else.

The one-sentence version

Upload the file over HTTP and get an instant receipt with a request_id; watch the asr.transcription.results RabbitMQ queue for a message with that same request_id to get the finished transcript — never poll, never assume ordering, always handle results idempotently.
